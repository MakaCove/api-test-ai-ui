# 项目优化与拓展方向 · 后续规划

本文档结合当前项目状态，梳理**优化方向**与**拓展方向**，并给出**后续实施规划**，便于按阶段、按优先级推进。

---

## 一、当前项目状态简要回顾

- **形态**：单体 Spring Boot，Thymeleaf 服务端渲染 + 原生 JS 调用 REST API。
- **已具备**：用户认证、项目管理、文档管理（粘贴/上传、AI 标准化与提取）、接口管理、用例管理、测试代码生成与导出、系统配置、分页、软删除、状态流、全局异常处理、工作台统计等。
- **暂未覆盖**（需求文档已标注）：多环境维度、细粒度权限（RBAC）、CI 集成、接口实际执行与报告、Swagger/OpenAPI 直接导入。

## 二、优化方向（在现有功能上做深）

### 2.1 代码与架构优化

| 方向 | 现状 | 优化建议 | 预期收益 |
|------|------|----------|----------|
| **统一返回结构** | 成功接口直接返回实体或 List/Page，无统一包装 | 定义统一成功响应体，如 `{ "success": true, "data": ..., "message"?: "" }`，便于前端统一解析与错误区分 | 前端处理一致、便于扩展分页/元数据 |
| **404 处理** | 资源不存在时可能抛异常或返回 404 未统一 | 在 GlobalExceptionHandler 中增加对「资源未找到」的异常类型，返回 404 + `{"message":"..."}`；Controller 层对查询单条资源统一先判空再抛自定义 NotFoundException | 接口语义清晰、前端可区分 400/404/500 |
| **DTO 与 VO 分层** | 部分接口直接返回 Entity | 对对外 API 引入 DTO/VO，避免暴露实体字段、便于版本演进与文档生成 | 接口稳定、易维护 |
| **服务层边界** | 部分逻辑在 Controller | 将业务逻辑下沉到 Service，Controller 只做参数校验、调用 Service、组装返回 | 可测试性、复用性提升 |
| **常量与枚举** | 状态等为字符串字面量 | 文档/接口/用例状态、代码状态等抽成枚举或常量类，减少魔法值 | 可维护性、避免拼写错误 |
| **接口文档** | 无集中 API 文档 | 引入 SpringDoc OpenAPI 3（或 Swagger），为 REST 接口生成文档与在线调试 | 前后端协作、对接第三方更方便 |

### 2.2 性能与稳定性优化

| 方向 | 现状 | 优化建议 | 预期收益 |
|------|------|----------|----------|
| **AI 调用超时与重试** | 依赖 SDK 默认超时 | 显式配置连接/读超时；对可重试错误（如 5xx、限流）做有限次数重试 + 退避 | 减少长时间挂起、提高成功率 |
| **异步任务可观测** | 标准化/提取/生成用例/生成代码为异步，无任务队列 | 为长时间任务分配任务 ID，前端可轮询任务状态或通过 SSE/WebSocket 推送进度；可选引入轻量队列（如内存队列 + 线程池）记录任务状态 | 用户可知进度、避免重复提交 |
| **列表查询性能** | 列表含关联数据（如所属文档名、用例数） | 避免 N+1：用批量查询或 JOIN 一次拉取；大列表考虑只查主表 + 按需加载关联 | 列表打开更快、数据库压力更小 |
| **缓存** | 无缓存 | 对系统配置（t_system_setting）、当前用户信息等低频变更数据做本地缓存（如 Caffeine），设置合理 TTL | 降低 DB 与配置读取延迟 |
| **连接池与 DB** | 使用 HikariCP 默认配置 | 按实际并发调优 maximumPoolSize、连接超时等；对关键 SQL 检查索引 | 高并发下更稳定 |

### 2.3 前端与交互优化

| 方向 | 现状 | 优化建议 | 预期收益 |
|------|------|----------|----------|
| **加载与空状态** | 列表加载时可能空白或闪烁 | 列表请求期间显示 Loading（骨架屏或 Spinner）；空列表、空搜索结果统一空状态文案与插图 | 体验更清晰 |
| **乐观更新** | 部分操作为等后端返回后再刷新 | 对删除、禁用/启用等可先在前端移除/更新 UI，请求失败再回滚并提示 | 操作反馈更快 |
| **表单校验** | 部分校验仅后端 | 关键表单增加前端必填、格式、长度校验，与后端 @Valid 一致 | 减少无效请求、提示更及时 |
| **移动端/窄屏** | 主要为桌面布局 | 侧栏在小屏可收折为抽屉；表格支持横向滚动（已有），重要列优先展示 | 多设备可用 |
| **无障碍** | 未系统考虑 | 关键按钮加 aria-label、表单 label 关联、焦点顺序合理 | 可访问性提升 |

### 2.4 安全与合规优化

| 方向 | 现状 | 优化建议 | 预期收益 |
|------|------|----------|----------|
| **会话与登出** | Spring Security 默认会话 | 配置会话超时、并发会话数；登出时服务端失效 Session/Token | 更符合安全基线 |
| **敏感配置** | AI Key 等存库或配置文件 | 生产环境优先从环境变量或保密管理服务读取，避免写死在配置或提交到仓库 | 降低泄露风险 |
| **请求限流** | 无限流 | 对登录、注册、AI 相关接口做 IP/用户维度的限流（如 Bucket4j 或 Spring 生态限流） | 防暴力与滥用 |
| **输入校验** | 有 @Valid、部分业务校验 | 对文件上传做类型与大小限制、对富文本/JSON 长度做上限与敏感词过滤 | 防注入与滥用 |
| **操作日志** | 无审计日志 | 关键操作（登录、删除项目、删除接口、导出代码等）写审计表或日志，便于追溯 | 满足审计与排查需求 |

### 2.5 可测试性优化

| 方向 | 现状 | 优化建议 | 预期收益 |
|------|------|----------|----------|
| **单元测试** | 可能缺失或覆盖少 | 对 Service 层（尤其是 AI 解析、状态流转）写单测；对工具方法、JSON 清洗等写单测；AI 调用可 Mock | 重构与回归更安全 |
| **集成测试** | 可能缺失 | 对关键 REST 接口写 @SpringBootTest + MockMvc 或 TestRestTemplate，使用 H2/内存库或 Testcontainers | 接口契约稳定 |
| **E2E** | 无 | 可选：对核心流程（登录→创建项目→上传文档→提取→生成用例→生成代码）做少量 E2E（如 Selenium/Playwright） | 发布前信心更高 |

### 2.6 运维与可观测性优化

| 方向 | 现状 | 优化建议 | 预期收益 |
|------|------|----------|----------|
| **健康检查** | 可能仅 Spring Boot 默认 /health | 提供 /actuator/health 并区分 liveness/readiness；依赖 DB、外部 AI 的可单独标识 | 便于 K8s/负载均衡探活 |
| **指标** | 无业务指标 | 使用 Micrometer 暴露 AI 调用次数、耗时、失败率；关键接口 QPS/延迟 | 可做监控与告警 |
| **日志规范** | 有日志，格式可能不统一 | 关键业务操作打结构化日志（如 JSON），包含 requestId、userId、操作类型；错误日志带上下文 | 排查与分析更方便 |
| **配置多环境** | 主要 application.yml | 使用 spring.profiles（dev/test/prod），敏感项用环境变量或外部配置中心 | 部署更灵活 |

## 三、拓展方向（新能力与新场景）

### 3.1 功能拓展

| 方向 | 描述 | 依赖与工作量 | 价值 |
|------|------|--------------|------|
| **多环境（dev/test/prod）** | 项目下可配置多套环境（Base URL、Header 等），生成代码或执行时按环境切换 | 表结构增加环境维；配置与生成/执行流程改造 | 更贴近实际使用场景 |
| **Swagger/OpenAPI 导入** | 支持上传或输入 Swagger/OpenAPI JSON 或 URL，解析为接口列表写入 t_api_info | 解析库（如 swagger-parser）+ 与现有接口模型映射 | 减少手工录入、与现有文档体系打通 |
| **接口实际执行与报告** | 在平台内对接口发起真实 HTTP 请求，记录请求/响应、状态码、耗时，并生成简单报告 | 需配置环境（URL、鉴权）；执行引擎；报告存储与展示 | 形成「设计→用例→代码→执行→报告」闭环 |
| **测试代码模板/规则** | 支持自定义代码模板（如类名规则、包名、断言风格）或选择不同测试框架（JUnit5/TestNG） | 模板引擎 + 配置项 + 多套生成逻辑 | 满足不同团队规范 |
| **用例标签与筛选** | 用例支持标签、模块；列表支持按标签/模块/优先级筛选与统计 | 表与索引、前端筛选组件 | 用例管理更清晰 |
| **项目/接口/用例导入导出** | 项目或接口列表导出为 JSON/Excel；支持从 JSON 导入接口或用例 | 序列化格式设计、导入校验与去重 | 备份、迁移、跨项目复用 |
| **版本/历史** | 接口或用例的修改历史、生成代码的历史版本可查看或回滚 | 历史表或版本号字段；列表与详情展示 | 可追溯、可回滚 |

### 3.2 用户与权限拓展

| 方向 | 描述 | 依赖与工作量 | 价值 |
|------|------|--------------|------|
| **角色与权限（RBAC）** | 引入角色（如管理员、普通用户、只读），对项目/接口/用例的增删改查做权限控制 | 角色表、权限表、与项目/资源关联；Spring Security 整合 | 多团队共用时的安全与隔离 |
| **多租户/工作空间** | 数据按租户或工作空间隔离，不同团队看到不同项目集合 | 表增加 tenant_id/workspace_id；查询与写入全局过滤 | 支持 SaaS 或大型组织 |
| **个人设置** | 用户可设置默认每页条数、主题（深/浅色）等 | 用户配置表或扩展 t_user；前端读取并应用 | 体验个性化 |

### 3.3 集成与生态拓展

| 方向 | 描述 | 依赖与工作量 | 价值 |
|------|------|--------------|------|
| **CI 集成** | 提供 Jenkins/GitLab CI/GitHub Actions 等流水线示例或插件，从平台拉取用例或代码并执行 | 开放「按项目/接口导出用例或代码」的 API；提供 pipeline 示例 | 自动化回归、与现有 DevOps 打通 |
| **Git 集成** | 将生成的测试代码直接提交到指定 Git 仓库或 MR | Git 客户端或 API；鉴权与权限管理 | 代码直接入库、协作顺畅 |
| **消息/通知** | 长时间任务（如批量生成代码）完成后通过站内消息或邮件/企微/钉钉通知 | 消息表、通知渠道抽象、异步发送 | 用户不必一直等待页面 |
| **多 AI 模型切换** | 系统配置中可选择不同模型（如 qwen/gpt/claude），或按任务类型选模型 | 配置项与 AiClientService 抽象；多模型适配 | 成本与效果可权衡 |

### 3.4 架构与部署拓展

| 方向 | 描述 | 依赖与工作量 | 价值 |
|------|------|--------------|------|
| **前后端分离** | 将前端拆为独立 SPA（如 Vue/React），后端仅提供 REST API | 前端工程化、鉴权改为 JWT 等；后端 CORS 与安全配置 | 前端迭代更快、可独立部署 |
| **异步任务队列** | 将 AI 标准化、提取、生成用例、生成代码放入消息队列（如 Redis List/RabbitMQ），由 Worker 消费 | 任务表、队列、Worker 进程 | 解耦、可扩展、任务可重试与监控 |
| **容器化与编排** | Dockerfile + docker-compose/K8s 编排，包含应用与 MySQL（及可选 Redis） | 镜像构建、健康检查、配置外置 | 部署标准化、易扩展 |
| **多实例与会话** | 多实例部署时 Session 共享（如 Redis Session）或改为无状态 + JWT | Spring Session Redis 或 JWT | 水平扩展、高可用 |

## 四、后续规划（分阶段、可执行）

### 4.1 原则

- **先优化再拓展**：在现有功能上补齐体验与质量，再加新能力。
- **小步迭代**：每阶段目标明确、可交付、可验证。
- **按价值与成本排序**：高价值、低成本优先；强依赖（如 RBAC 与多租户）可后置。

### 4.2 阶段一：体验与质量加固（建议 1～2 个迭代）

**目标**：不增加新业务功能，提升稳定性、可观测性和使用体验。

| 序号 | 事项 | 类型 | 优先级 |
|------|------|------|--------|
| 1 | 统一成功响应结构（可选）+ 404 处理（GlobalExceptionHandler + NotFoundException） | 优化 | 高 |
| 2 | 关键列表查询避免 N+1，必要时加索引 | 优化 | 高 |
| 3 | AI 调用超时与重试配置、失败提示清晰 | 优化 | 高 |
| 4 | 列表 Loading、空状态统一 | 优化 | 中 |
| 5 | 系统配置等低频数据本地缓存（Caffeine） | 优化 | 中 |
| 6 | 健康检查 /actuator/health 配置完善（含 DB） | 优化 | 中 |
| 7 | 状态、类型等抽成枚举/常量，减少魔法值 | 优化 | 中 |
| 8 | 核心 Service 单测 + 关键 REST 接口集成测试 | 优化 | 中 |

**交付物**：接口语义更清晰、列表与 AI 更稳、有基础测试与健康检查。

### 4.3 阶段二：功能小步拓展（建议 2～3 个迭代）

**目标**：在现有主流程上增加 1～2 个高价值、可独立交付的能力。

| 序号 | 事项 | 类型 | 优先级 |
|------|------|------|--------|
| 1 | Swagger/OpenAPI 导入：上传或输入 URL 解析为接口列表 | 拓展 | 高 |
| 2 | 项目/接口导出为 JSON；接口从 JSON 导入（含去重与校验） | 拓展 | 高 |
| 3 | 接口文档（SpringDoc OpenAPI 3）生成与在线调试 | 优化 | 中 |
| 4 | 异步任务进度：为长时间任务分配任务 ID，前端轮询状态或 SSE | 优化 | 中 |
| 5 | 关键操作审计日志（登录、删除项目/接口、导出代码等） | 优化 | 中 |
| 6 | 请求限流（登录、注册、AI 相关接口） | 优化 | 中 |

**交付物**：可从 Swagger 快速导入接口；支持导入导出便于备份与迁移；接口有文档、任务可查进度、有审计与限流。

### 4.4 阶段三：场景深化与集成（建议 2～4 个迭代）

**目标**：围绕「执行」与「协作」延伸，或做多环境/权限。

| 序号 | 事项 | 类型 | 优先级 |
|------|------|------|--------|
| 1 | 多环境（dev/test/prod）：项目下配置 Base URL 等，生成代码按环境 | 拓展 | 高 |
| 2 | 接口实际执行：在平台内发起请求、记录结果、简单报告 | 拓展 | 高 |
| 3 | 角色与权限（RBAC）：项目级可见/可编辑角色 | 拓展 | 中 |
| 4 | CI 示例：提供 Jenkins/GitLab/GitHub Actions 调用平台 API 执行用例的示例 | 拓展 | 中 |
| 5 | 消息/通知：长时间任务完成后站内消息或邮件 | 拓展 | 中 |
| 6 | 测试代码模板或框架选择（如 JUnit5/TestNG） | 拓展 | 低 |

**交付物**：支持多环境与真实执行形成闭环；多人在线时有权限控制；可与 CI 与通知打通。

### 4.5 阶段四：架构与规模（按需）

**目标**：在有多实例、多团队或 SaaS 需求时再考虑。

| 序号 | 事项 | 类型 | 优先级 |
|------|------|------|--------|
| 1 | 异步任务队列（Redis/RabbitMQ）+ Worker，任务可重试与监控 | 拓展 | 按需 |
| 2 | 前后端分离（SPA + JWT）+ 后端仅 API | 拓展 | 按需 |
| 3 | 多租户/工作空间数据隔离 | 拓展 | 按需 |
| 4 | 容器化（Dockerfile）+ docker-compose/K8s，Session 共享或无状态 | 拓展 | 按需 |

## 五、优先级矩阵（参考）

| 维度 | 高价值 + 低成本 | 高价值 + 高成本 | 低价值 + 低成本 | 低价值 + 高成本 |
|------|------------------|------------------|------------------|------------------|
| 示例 | 404 处理、列表 N+1、Loading/空状态、状态枚举、Swagger 导入、导入导出 | 接口实际执行、RBAC、多环境 | 健康检查、缓存、审计日志、限流 | 多租户、前后端分离、任务队列 |
| 建议 | 优先做 | 分阶段做、做 MVP | 有空就做 | 有明确需求再做 |

## 六、总结与建议

- **短期（1～2 个月）**：以**阶段一**为主，把 404、N+1、AI 超时与重试、Loading/空状态、健康检查、常量/枚举、基础单测与集成测做完，再视情况加 1～2 项阶段二（如 Swagger 导入、导入导出）。
- **中期（3～6 个月）**：完成**阶段二**，并启动**阶段三**中的多环境与接口执行、RBAC、CI 示例、通知等，按业务优先级选做。
- **长期**：根据是否多实例、多团队、SaaS 化，再规划任务队列、前后端分离、多租户、容器化等（阶段四）。
